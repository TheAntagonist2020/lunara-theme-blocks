## Canonical state and adoption

Keep brand, columns (headings), copyright unchanged. Add navigation = { mode: inherited|custom, columns: { editorial: [], oscars: [], utility: [] } }. Each dense ordered list has at most12 items; item exact shape { id, enabled, label, destination, url }. Stable bounded ASCII IDs unique across the editor; enabled strict boolean; label plain text1–80 characters; destination exact built-in enum or custom; custom URL required, max2048 characters. Built-in items require url empty so an obsolete saved URL cannot override a dynamic destination. Suggested built-ins mirror the actual footer: home/reviews/journal/about/editorial-policy/oscars/categories/ceremonies/ledger/search/contact/rss/privacy. Allow repeated destinations with distinct IDs; reject duplicate IDs and sparse arrays.

One new theme mod lunara_footer_navigation stores a canonical JSON string { version:1, columns:... }. Its valid presence is adoption; no separate flag or competing WP menu storage. API navigation.mode is derived on read, not blindly trusted as proof of prior adoption. Missing mod seeds editor rows from the existing hardcoded defaults with stable IDs but leaves public output and storage untouched. Editing a row or selecting an explicit Use these lists action switches candidate to custom; Preview renders it privately; Apply persists adoption. A copy-only Apply while inherited must leave the new mod absent. Explicit custom empty lists stay empty. If Reset is offered, label it clearly: reverting to inherited navigation removes this mod only through Apply. Old clients missing navigation must preserve the current mod rather than adopt, reset or overwrite it.

Extract the present hardcoded lists in inc/frontend.php:1467+ into an inherited-list resolver used by both the editor seed and public renderer. Preserve the exact current labels, fallback URLs and conditional Privacy behavior. Store built-in keys, resolve archive/feed/Privacy/Search URLs on every render; omit unavailable destinations, retain them in editor with explanation. Preserve the separate legal Privacy row, logo, six scalar fields and registered footer-* menu data. Do not change footer.php or guarded monolith copies.

## Final alignment with Search/404 design

This decision supersedes the earlier suggestion to accept old clients missing navigation. New Footer save/Preview POST candidates must contain the complete current schema; reject old or partial bodies with a reload instruction before writes. Compatibility is limited to exact historical History snapshots and already authenticated old preview tokens. Do not infer a legacy shape from arbitrary missing fields.

A small shared pure revision helper is justified for Footer and Search only: callers supply explicit current and frozen legacy key lists; validate the exact historical snapshot using valid_mod_snapshot; append CURRENT raw snapshot entries for the newly owned keys, preserving value types and absence. Reject near-legacy shapes, unknown keys and malformed entries. The surface caller retains safety revision creation, transaction and rollback ownership. Do not introduce a generic fill-missing-fields helper or change generic candidate validation.

Keep old-token recognition and filter installation surface-specific, after ordinary owner/user/route/hash/expiry authentication. Exact old tokens install only their historical field filters; appended fields retain current public values and adoption state. Never rewrite token state or extend expiry. The new 404 surface has no historical family migration requirement.

Root has accepted explicit adoption and one canonical JSON scalar in principle; no further user storage confirmation is needed. Follow-up: implement the narrow snapshot helper once with both Footer and Search compatibility matrices, then the scoped providers/editors.
